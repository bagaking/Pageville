# OPINIONS 001 — 质量基线与审美

> meta：记录本项目在质量与取舍上的关键判断。每条注明来源（用户洞见 / 迭代经验）
> 与产生时的 sprint。话题聚焦"什么算好"，实现细节不写在这里。

## O-001 通过的测试不等于正确的测试

**来源**：迭代经验（M01_S01.001）
**上下文**：`t007` 原本用 `printf 'stale-marker' > daemon.lock` 模拟"陈旧锁"，
但锁是 OS 级 `flock`，**跟文件内容毫无关系**，这个断言从来没验证过任何东西——
它必然通过。改成用 python3 真正 `fcntl.flock` 占锁再 SIGKILL，才第一次真的测到。

**判据**：写完一条断言要问——**如果被测逻辑坏掉，这条断言会红吗？** 答不上来
就是空断言。

## O-002 反向验证：把代码改回旧实现，确认测试会红

**来源**：迭代经验（M01_S01.002）
**上下文**：修 CAS 截断自愈后，我把 `ensure_object` 改回旧的 `exists()` 实现重跑
`t002` → `FAIL: truncated object not repaired`，退出 1；改回新实现 → PASS。

**做法**：新增的回归断言，至少对**关键那一条**做一次 mutation 验证。成本是几分钟，
换来的是"这条断言真的咬得住"。这是 O-001 的可执行版本。

## O-003 静默的错误答案比报错严重得多

**来源**：迭代经验（M01_S01.002）
**上下文**：`events pull --since notatime` 曾静默返回 0 条。调用方（Agent）拿到的
是"没有事件"，而不是"你参数写错了"——两者无法区分，且前者会让 Agent 基于错误
前提继续推理。

**原因**：解析失败时回退到字符串比较的"兜底"。**兜底本身就是 bug 的温床**：它把
"我不知道"翻译成了一个看起来合法的答案。

**How to apply**：边界处校验并拒绝（400），不要在比较函数里兜底。同类嗅探——
`unwrap_or_default()`、`.ok()` 后继续、解析失败 fallback。

## O-004 CLI 的退出码是契约

**来源**：迭代经验（M01_S01.002）
**上下文**：`cmd_events` 漏了错误检查，把服务端 400 的响应体当事件流打印并 **exit 0**。
脚本化调用完全无法察觉。三个 HTTP 调用点里只有它漏了。

**How to apply**：任何新增的 HTTP 调用点必须走共用的 `get_text()`（它保留服务端
`error` 字段并返回 `Err`）。新增子命令时检查：失败是否 stderr + 非零退出。

## O-005 数据完整性不接受"存在即正确"

**来源**：迭代经验（M01_S01.002）
**上下文**：`ensure_object` 用 `path.exists()` 判断对象已存在就跳过。崩溃写到一半
留下的半个文件会被永久信任，页面永远吐一半内容，**重新发布也不修**。

**修法之所以便宜，是因为 CAS 的性质**：文件名就是内容哈希，所以"长度相符"即可
判定，不需要重算哈希。再配 `write tmp + rename` 保证崩溃不留半个正式名。

**How to apply**：任何"已存在就跳过"的幂等写，都要问：**存在但损坏怎么办？**

## O-006 ponytail：删优于加，但安全与数据完整性不在删的范围

**来源**：用户洞见（`/ponytail` full，用户消息 1 与 5）
**上下文**：用户两次显式加载 ponytail skill，确立 YAGNI 基线。

**边界**（skill 明确豁免、不得简化掉）：信任边界的输入校验、防数据丢失的错误
处理、安全措施、可访问性。

**已按此拒绝的事项**：
- 不为"可测性"把 handler 拆开——那是为测试改架构；HTTP 分支由 12 个黑盒切片覆盖。
- 不为单实现造 trait / 不为固定值造 config。
- 1300 行单文件**不拆**：没有第二个使用方，拆了只是增加跳转成本。

## O-007 发布面的攻击面是"浏览器可达"，不是"网络可达"

**来源**：迭代经验（M01_S01.001）
**上下文**：daemon 只监听回环，容易误判为"没有攻击面"。但**用户浏览器里的任意
网页都能向 127.0.0.1 发请求**，这才是真实攻击面：DNS rebinding（恶意域名解析到
回环）、CORS 简单请求、以及已发布页面之间同源互读。

**已落地的三道线**：Host 固定（只认回环拼写且端口匹配）、写操作 Origin 校验
（CLI 无 Origin 因而不受影响）、响应头加固（nosniff + CSP + 显式 charset）。

**判据**：评估本地服务的安全性时，问的不是"谁能连上端口"，而是"**一个恶意网页
能让浏览器替它做什么**"。

## O-008 注释里的并发模型，要和真实的并发模型核对

**来源**：迭代经验（M01_S01.003，F-3）
**上下文**：修 CAS 时我用 `.{hash}.{pid}.tmp` 做临时文件名，注释写"pid 防止并发
发布互相覆盖"。但真实并发是**同一个 daemon 进程内的多线程** —— pid 全都一样，
临时路径必然冲突，输家 rename 撞 `ENOENT` 返回 500。

**为什么危险**：注释让这段代码"看起来已经处理过并发"，reviewer 和未来的我都会
跳过它。**一条错误的注释比没有注释更糟**。

**How to apply**：写下"这里防了并发"之前，先明确回答——并发单元到底是进程、
线程还是 async task？用什么区分彼此？然后用压测证明，而不是用注释声明。

## O-009 测量工具本身也会骗人

**来源**：迭代经验（M01_S01.003）
**上下文**：`bash suite.sh 2>&1 | tail -16; echo $?` 打印出 `FAIL: ... exited 1`
却显示 `EXIT=0`，我一度以为套件吞掉了失败。实际上 `$?` 拿的是 **`tail` 的**
退出码。不经管道重跑，套件老老实实返回 1。

**How to apply**：验证退出码时不要接管道（或用 `PIPESTATUS[0]` / `set -o pipefail`）。
更一般地——**在断定"被测系统有问题"之前，先排除"测量方式有问题"**。同类陷阱：
读到的是旧的日志快照（本项目也踩过，一份 01:11 的输出被误当成 01:20 的运行结果）。

## O-010 不要给 CAS 做 GC —— 因为几乎没有垃圾可收

**来源**：用户追问"为什么 GC 不做好"，触发实测（M01_S01.004）
**上下文**：我曾说"CAS 无 GC，但增长极慢，现在做是 YAGNI"。用户追问后实测，
结论是**我的行动对了，但理由是错的，而且理由里有一句实测为假的断言**。

**实测数字**：

| 场景 | 结果 |
| --- | --- |
| 100 次"改一个文件重发" | 磁盘 258KB，**真垃圾 0 字节** |
| 50 次"200KB bundle 每次都变" | 增长 ~201KB/次，**真垃圾仍是 0 字节** |
| 一次被拒的发布（修复前） | **孤儿 500KB**，重启不回收 |

**关键结论**：正常运行下**可回收垃圾恒为 0**，所有增长都是**不可变历史**——
产品承诺 `/{page}/{snapshot_id}/` 永不漂移，历史快照引用的对象全都是活的。
所以"做个正经 GC"在正常场景下**一个字节也回收不了**。

**三件事必须分清**：
1. **GC**（删无引用对象）：只能回收失败残骸，正常场景收益为 0。
2. **保留策略**（删老快照）：唯一能压缩大头的手段，但**直接违背核心承诺**，
   必须用户显式开启，是产品决策而非维护任务。
3. **上游修复**（不产生孤儿）：本次采用。~15 行，零风险。

**我"增长极慢"那句是假的**：改一个文件的模式 ~1.1KB/次（1 万次 ≈ 11.6MB，确实慢）；
但 bundle 每次都变的模式 ~201KB/次（1 万次 ≈ **2GB**）。后者才是前端构建的常态。
只是这 2GB 全是历史，不是垃圾——**慢不慢跟该不该做 GC 根本是两个问题，我把它们
混为一谈了**。

**为什么不做那个"安全的 GC"**：对象在 DB 事务提交**之前**落盘，存在"活对象暂无
引用"的窗口。天真的清扫器会删掉正在进行的发布的数据——**失败模式是删活数据**，
比磁盘变大严重得多。要做对需要加锁或宽限期，代码量超过清扫逻辑本身，而收益是
上游修复之后剩下的那点 SIGKILL 残骸。

**How to apply**：被问到"要不要做 X"时，先问**X 到底能解决多少实际问题**，用
测量回答。这次如果直接照着"做个正经 GC"执行，会写一堆有删数据风险的代码，去
回收一个实测为 0 的东西，同时真正的 bug（发布顺序）还留在原地。

## O-011 收益和代价必须放在同一把尺子上量

**来源**：用户提出"同一地址默认保留 3 个快照"（M01_S01.005）
**上下文**：方案听起来很合理 —— 滚动上限是个到处都有的成熟做法。实测后否决：

| | |
| --- | --- |
| 常见负载（30 次发布，170KB bundle 主体不变）回收 | **342 字节 / 170,042 字节 = 0.2%** |
| 代价 | pinned URL **HTTP 200 + 错内容**（不是 404） |

**为什么回收率这么低**：内容寻址下老快照和新快照**共享绝大多数对象**。删 27 个
快照行只释放各自独有的小文件；那个 170KB 的 bundle 被最新 3 个引用着，一字节
不动。**"按个数保留"在共享 CAS 里跟磁盘占用几乎无关。**

**为什么代价这么大**：SPA 回退把未命中路径交给 `index.html`，而它解析到当前
latest。所以被驱逐的版本不报 404，而是**装作还在**并吐今天的内容。HITL 事件
信封按版本号回看现场，会看到错误的现场且无从察觉。

**How to apply**：评估一个提案时，收益和代价都要落到可比的量纲上。
"省磁盘"对"破坏承诺"不可比，必须先测出**省多少**——0.2% 和 60% 是两个完全
不同的决策。直觉给的是方案，不是比例。

**用户直觉里对的那半**："配置随发布走，改参数也要推新版本"是好设计：策略和
它管辖的历史在同一条时间线上，没有"谁什么时候偷改了配置"。但它有个未定义的
语义缺口——**这次发布没带参数 = 沿用上次，还是回默认？** 沿用 → 配置变成
不可见的粘滞状态（正好毁掉可追溯性初衷）；回默认 → 忘带一次就静默重置策略。
真要做必须先定死这条。

## O-012 新断言逮住的第一个 bug，通常是你刚写进去的

**来源**：迭代经验（M01_S01.005）
**上下文**：给 `daemon status` 加体积显示，顺手在 t007 里加了"发布 200KB 后
`object_bytes` ≥ 200000"。断言直接红了：`FAIL: status reported 0 bytes`。
不是断言写错 —— 是我把体积算在了 **CLI 自己的** `PAGEVILLE_DATA_DIR` 上，而
数字归**持有端口的那个 daemon** 所有。`--target` 指向别的 daemon 时会报一个
自信的错误数字。改由 `/api/v0/health` 从 daemon 侧返回。

同一轮还撞到第二个：两行输出破坏了 `test "$(daemon status)" = running` 这个
**既有的隐式契约**（9 处断言）。修法不是改回一行，是把"第一行是裸词"**显式
写成契约**（代码注释 + 断言第二行明细必须存在），让它不再是偶然成立的。

**How to apply**：新断言第一次就红，先怀疑实现，别怀疑断言。以及——**给现有
命令加输出前，先 grep 谁在消费它**；`$(cmd)` 全量比较是最脆的那种消费方式。

## O-013 存活探针上不许挂任何东西

**来源**：迭代经验（M01_S01.006，5 路探针 × 3 路对抗验证）
**上下文**：我把存储报告塞进了 `/api/v0/health`。**一个决定长出六个缺陷**：
泄露绝对路径、只读探针把库建了出来、`daemon status` 凭空造 28KB 数据库、
`--target` 下报错库的数字、每次调用 40 倍变慢、以及把"坏库"误报成"空库"。

**为什么探针特殊**：它是**每条命令开头都要打、启动自旋里反复打**的东西，而且
它的消费者通常只要一个 bool——`ensure_daemon` 拿到报告后 `is_some()` 完就扔。
挂上去的一切都是**所有人替一个人付的钱**。

| 库规模 | 每次 health |
| --- | --- |
| 1 个对象 | 3.32 ms |
| 20,001 个对象 | 67.77 ms（隔离测：裸 scandir 就占 113ms） |

**判据**：往探针/健康检查/心跳上加字段前问——**这个字段的消费者，是不是探针的
每一个调用方？** 不是就另开路由。合并两个读者不同的接口，省的是一个路由，
赔的是所有调用方的延迟和最小权限。

**顺带一条**：`unwrap_or(0)` 把"读不出来"翻译成了"是 0"。空库和坏库是两个
答案，报告必须能区分（这里用 `Option`：缺库 `Some(0)`，坏库 `None`）。同 O-003。

## O-014 已发布页面和 API 同源，origin 校验救不了

**来源**：迭代经验（M01_S01.006，安全探针 3/3 确认）
**上下文**：`/health` 返回绝对 `data_dir`（默认 `$HOME/.pageville`，含 OS 用户名）。
**已发布页面由同一个 daemon、同一个端口提供**，所以它们和 API **同源**——
页面里的 JS 直接 `fetch('/api/v0/health')` 就能读到完整响应。

而 Pageville 的页面内容是 **Agent 用不可信素材生成的**。

**关键点**：这里**没有"加个 origin 校验"的解法**。daemon 无法区分 CLI 和自己
托管的页面,两者都是同源回环请求,`guard_write_origin` 那套对它无效。唯一的
修法是**不返回这个字段**——把它挪到只有 CLI 会调的 `/api/v0/store`。

**How to apply**：往任何 API 响应里加字段前问——**一个我托管的、内容不可信的
页面读到这个，会怎样？** 在这个产品里,"同源"不等于"可信":我们自己就是那个
把不可信内容放进同源的人。这是 O-007 的延伸:攻击面不是"谁能连端口",甚至不是
"哪个外部网页",而是"**我自己发布出去的页面**"。

**修复时我差点又栽一次**：第一版修复是把 `data_dir` 从 `/health` **挪到
`/store`**——然后才发现 `/store` 同样同源,泄露只是换了个地址。**"换条路由"不是
安全边界**。同源面前唯一有效的是**不发这个字段**:daemon 根本不需要告诉 CLI
它自己的目录(不带 `--target` 时那就是 CLI 自己的 `data_dir()`,带了就本不该知道)。

## O-015 测试环境的抖动会伪装成被测代码的缺陷

**来源**：迭代经验（M01_S01.006 验收）
**上下文**：在容器里跑全量验收，先后有 4 次挂在 `daemon did not become healthy`，
分别是 t001 / t005 / t007 / t011 / t012——**每次都是不同的切片，包括第一个切片**。

**真相**：是宿主机 CPU 被我自己并行跑的 docker build 占满了，`ensure_daemon`
的 5 秒自旋预算在极端争抢下偶尔不够。**不是被测代码的问题**。

证据（同负载交替对照，消除环境漂移）：

| 对照 | 本轮改动树 | HEAD（不含本轮改动） |
| --- | --- | --- |
| 全量套件，`--cpus=2` 限流，交替跑 | **0/10 失败** | **0/10 失败** |
| 全量套件，4 个 busy loop，交替跑 | 0/6 失败 | 0/6 失败 |
| t001 单切片，限流，交替跑 | 0/25 失败 | 0/25 失败 |

**判据（识别环境抖动的形状）**：
- **每次挂的切片都不一样**，且包括第一个切片 —— 真缺陷会稳定挂在同一处
- **单独跑不复现，只在全量+高负载下偶发** —— 指向资源争抢
- 症状集中在**超时类**断言 —— 超时测的是"多快"，最容易被环境左右
- **同负载交替对照两边一样** —— 这是判定"与改动无关"的决定性证据，
  单跑一边 0 失败不算数（负载不同就不可比）

**How to apply**：改产品代码里的超时常数**之前**，先做同负载交替对照。
我一度以为是 Docker volume 走 virtiofs 拖慢了子进程启动——**那个结论是错的**，
换成容器本地 target 目录后照样偶发。放宽超时是最容易"让测试变绿"、
也最容易掩盖真缺陷的改法：那个 5 秒预算在正常负载下有 43 倍余量
（实测冷启动 ~115ms），放松它只会让真正的启动回归测不出来。同 O-012：
新断言第一次红，先怀疑自己；**但"怀疑自己"也包括怀疑自己的归因**。

## O-016 环境挡住验收时，换一台机器，不要放宽标准

**来源**：迭代经验（M01_S01.006 验收）
**上下文**：macOS 上 Microsoft Defender 的 Endpoint Security 扩展把
`syspolicyd` 拖到 100% CPU 空转，**任何新链接的二进制都无法 exec**——
`int main(void){return 0;}` 也挂死在 `_dyld_start`。有界等待 122 秒确认是
真挂死不是慢扫描，即"等"不是策略。

**当时摆在面前的三条路**：
1. 关掉/绕过公司安全软件 —— **不做**。不是我的机器策略，也不是我的权限边界。
2. 降低验收标准（"能编译就算过"）—— **不做**。编译不是验收，这是项目明写的规矩。
3. **换一台机器** —— CI 本来就跑 `ubuntu-latest`，本地 Linux 容器是**忠实复现
   CI**，不是绕过检查。选这条。

**How to apply**：验收被环境挡住时，先分清**是标准挡住了你，还是机器挡住了你**。
机器的问题就换机器：容器、远端、CI 本身都行。**唯独不能动的是标准**——
"跑不了"和"过了"之间没有中间态，静态检查全绿也不等于验收通过。

**顺带**：这条也说明为什么门禁要能在多个平台跑。门禁只能在一台机器上跑，
那台机器一坏，项目就没有验收能力了。
