# M01_S01.006.FIX — 撤销探针过载：/health 回归廉价，存储报告独立成路由

> meta：记录一轮对抗探测（5 路探针 × 3 路对抗验证 = 35 agent）的结论与修复。
> 触发：用户「优化」。本轮所有确认缺陷都由**上一次提交 d85cc9f 自身引入**。
> 状态：**已验收**（Linux 容器内跑通完整 CI 门禁，见文末「验收记录」）。

## 一句话根因

上一轮我把**存储报告塞进了 `/api/v0/health`**。一个决定，长出六个缺陷。

`/health` 是存活探针：每条 CLI 命令开头打一次，`ensure_daemon` 启动自旋里还要
反复打。它必须**常数时间、无副作用、无敏感信息**。我给它加了全量目录扫描 +
建库 + COUNT。

## 确认的缺陷（均经 3 路对抗验证，独立复现）

| # | 性质 | 缺陷 | 票数 |
| --- | --- | --- | --- |
| 1 | **security** | `/health` 把绝对 `data_dir`（含 $HOME/OS 用户名）暴露给**同源的已发布页面** | 3/3 |
| 2 | correctness | 只读探针调 `db()` → `create_dir_all` + DDL，**把它本该报告的库给创建了**，然后报 `snapshots:0` 装作库一直是空的 | 3/3 |
| 3 | contract | `daemon status` 对着**停止的 daemon** 也会凭空造出 28KB 的 `pageville.db`（此前是纯网络探针，零文件系统访问） | 3/3 |
| 4 | contract | `--target` 指向已停止的 daemon 时，把**调用方自己的**库大小当作 target 的答案打印 | 3/3 |
| 5 | performance | 每次 health 全量重算：0 对象 ~5ms（vs 父提交 0.127ms，**40 倍**），20k 对象 ~50-68ms | 2/3 |
| 6 | deletable | `serve_page` 里不可达的 `parts.is_empty()` 分支；`EventEnvelope` 的 `Deserialize`+`Clone`、`EventQuery` 的 `Default` 三个死 impl | 2/3, 3/3 |

### #1 为什么是真的安全问题

**已发布页面和 API 同源**——同一个 daemon、同一个端口。所以一个 Agent 用不可信
内容生成的页面，它的 JS 直接 `fetch('/api/v0/health')` 就能读到完整 JSON。

这里没有"加个 origin 校验"的解法:daemon **无法区分** CLI 和已发布页面,两者都是
同源回环请求。唯一的修法是**不返回这个字段**。

（对比被否决的一条：有探针报告 `/health` 缺 nosniff 头。1/3 票，驳回——JSON
响应不是浏览器渲染面，且该路由不返回用户内容。）

### #5 实测数字（我自己独立测过，不只信 agent）

| 库规模 | 每次 health |
| --- | --- |
| 1 个对象 | 3.32 ms |
| 20,001 个对象 | 67.77 ms |

隔离测量：20k 文件的裸 `scandir+stat` 就要 113ms。成本主体是目录扫描，随对象数
线性增长。而这笔钱**每条 CLI 命令都在付**，`ensure_daemon` 那个消费者甚至
`is_some()` 完就把报告扔了——纯粹白算。

## 修法：撤销过载，而不是给六个症状打六个补丁

```
/api/v0/health  → 回到常数 JSON（status/protocol/version），零 FS、零 DB
/api/v0/store   → 新路由，只有 daemon status 会调
```

外加一个 `snapshot_count()`：

- **不走 `db()`** —— 报告不该创造它所报告的对象
- 库不存在 → `Some(0)`；库**读不出来** → `None`（`snapshots: null`）。
  "空库"和"坏库"是两个不同的答案,`unwrap_or(0)` 会把后者伪装成前者
- 用 **read-write-without-create** 而非 read-only 打开：验证者发现 WAL 库静息时
  没有 `-shm` 伴生文件,真 read-only 打开会直接失败——那样每次都报 0,比原缺陷更糟

`daemon status` 的回退改为 `cli.target.is_none()` 才生效:有 `--target` 时本地库
就是**另一个库**(系统里根本不存在 port → data_dir 的绑定),宁可不报也不能编。

### 修复过程中我差点犯的第二次同样的错

第一版修复我把 `data_dir` **从 `/health` 挪到了 `/store`** ——然后在检查路由守卫
时才意识到:**`/store` 也是同源的**。已发布页面的 JS 照样能读。我只是把泄露换了
个地址,一个字节也没堵住。

**"换条路由"不是安全边界**。真正的修法是这个字段**哪条路由都不发**:daemon 不
需要告诉 CLI 它自己的数据目录——不带 `--target` 时那本来就是 CLI 自己的
`data_dir()`;带 `--target` 时 CLI **本来就不该知道**(见上一段)。

这条被单独固化成断言:`/store` 响应里出现 `data_dir` 直接 FAIL。

### 一条被对抗验证救回来的细节

探针建议用 **read-only** 打开数据库。验证者指出这会坏——我独立复现确认了:

```
干净关闭后的 WAL 库（-shm/-wal 已 checkpoint 掉，只剩 x.db）：
  mode=ro  → FAILED: unable to open database file
  mode=rw  → COUNT: 1
```

**这正是 daemon 正常停止后的磁盘状态**。照探针的建议改,每次离线查询都会报
`snapshots: null`(读不出来),比原缺陷更糟。所以用的是
**read-write-without-create**:不建库,但能读。这条已写成单测钉死。

### 顺带做的全响应面审计

O-014 既然成了原则，就不能只修被点名的那条路由。把**所有可能进入 HTTP 响应体的
主机路径**过了一遍：

- `st.data` / `data_dir()` 的全部 20 处引用 —— 除已修的 `api_store` 外，其余都只
  用于**拼接文件系统路径去读数据**，不进响应体
- 唯一的 `p.display()`（`collect_files` 里跳过符号链接的告警）是 **CLI 侧 stderr**，
  不经过 HTTP
- 21 处 `json!({"error": ...})` 错误体**全是固定字符串**，不含路径、不含内部状态
  （唯一带插值的是 `"{name} must be an RFC3339 timestamp"`，`name` 是参数名字面量）

结论：泄露面已清零，不只是被点名的那一条。

## 验收记录：绕过 macOS 环境阻塞，在 Linux 容器内跑完整门禁

验收一度被环境卡住：这台机器**无法启动任何新链接的二进制**——`int main(void){return 0;}`
编译后运行也一样，无限挂死在 `_dyld_start`，进程连 `main` 都没进。实测**界定为真挂死
而非慢扫描**：有界等待 122 秒仍未放行。根因是 Microsoft Defender 的 Endpoint Security
扩展在 `exec` 前拦截，配套 `syspolicyd` 100% CPU 空转 4+ 小时。公司安全软件，
**不关闭、不绕过**。

解法不是等，是**换一台机器**：CI 本来就跑在 `ubuntu-latest`，所以在本地 Linux 容器里
跑同一套门禁不是"绕过检查"，而是**忠实复现 CI**。macOS 的 Endpoint Security 不管辖
容器内的 exec，二进制正常启动。

| CI 步骤（`.github/workflows/ci.yml`） | 结果 |
| --- | --- |
| `cargo fmt --check` | 通过（macOS） |
| `cargo clippy --all-targets --locked -- -D warnings` | **0 警告**（macOS） |
| `cargo test --locked` | **10/10 通过**（容器 + 原生 macOS 各一遍） |
| `node scripts/npm/check.js` | 通过（`pageville@0.1.0; 7 runtimes`） |
| `bash scripts/verify/t008-acceptance.sh` | **12/12，exit 0**（容器限流交替对照 10/10 次；原生 macOS 补跑一遍） |

**后续**：`syspolicyd` 重启后本机恢复执行能力，已在原生 macOS 上补跑
`cargo test` 10/10 与 `t008-acceptance` 12/12（exit 0），两条路由的响应体与容器内
逐字一致。**同一份改动在两个平台独立确认过**，不只依赖容器这一个环境。

### 一个被误判成缺陷的环境抖动（以及我一次错误归因）

容器里跑全量验收，前后有 4 次挂在 `daemon did not become healthy`，分别落在
t001 / t005 / t007 / t011 / t012——**每次都是不同的切片，包括第一个切片**。

我第一次归因说是 Docker volume 走 virtiofs 拖慢了子进程启动。**这个结论是错的**：
换成容器本地 target 目录后照样偶发。真实原因是宿主机 CPU 被我自己并行跑的
docker build 占满，`ensure_daemon` 的 5 秒自旋预算在极端争抢下偶尔不够。

**同负载交替对照**（改动树与 HEAD 交替跑，消除环境漂移）：

| 对照条件 | 本轮改动树 | HEAD（不含本轮改动） |
| --- | --- | --- |
| 全量套件，`--cpus=2` 限流 | **0/10 失败** | **0/10 失败** |
| 全量套件，4 个 busy loop | 0/6 失败 | 0/6 失败 |
| t001 单切片，限流 | 0/25 失败 | 0/25 失败 |

两边完全一致 → **与本轮改动无关**。`ensure_daemon`／自旋预算／启动锁本轮
一行未动（`git diff` 已核）。正常负载下冷启动实测 ~115ms，对 5 秒预算有
**43 倍余量**——所以**没有**去放宽那个超时：那会为了迁就一个环境问题，
把真正的启动回归也一起测没了。

教训见 O-015：**"怀疑自己"也包括怀疑自己的归因**。
