# OPINIONS 001 — 质量基线与审美

> meta：记录本项目在质量与取舍上的关键判断。每条注明来源（用户洞见 / 迭代经验）
> 与产生时的 sprint。话题聚焦"什么算好"，实现细节不写在这里。

## O-001 通过的测试不等于正确的测试

**来源**：迭代经验（M01_S01.001）
**上下文**：`t007` 原本用 `printf 'stale-marker' > daemon.lock` 模拟"陈旧锁"，
但锁是 OS 级 `flock`，**跟文件内容毫无关系**，这个断言从来没验证过任何东西——
它必然通过。改成用 python3 真正 `fcntl.flock` 占锁再 SIGKILL，才第一次真的测到。

**判据**：写完一条断言要问——**如果被测逻辑坏掉，这条断言会红吗？** 答不上来
就是空断言。

## O-002 反向验证：把代码改回旧实现，确认测试会红

**来源**：迭代经验（M01_S01.002）
**上下文**：修 CAS 截断自愈后，我把 `ensure_object` 改回旧的 `exists()` 实现重跑
`t002` → `FAIL: truncated object not repaired`，退出 1；改回新实现 → PASS。

**做法**：新增的回归断言，至少对**关键那一条**做一次 mutation 验证。成本是几分钟，
换来的是"这条断言真的咬得住"。这是 O-001 的可执行版本。

## O-003 静默的错误答案比报错严重得多

**来源**：迭代经验（M01_S01.002）
**上下文**：`events pull --since notatime` 曾静默返回 0 条。调用方（Agent）拿到的
是"没有事件"，而不是"你参数写错了"——两者无法区分，且前者会让 Agent 基于错误
前提继续推理。

**原因**：解析失败时回退到字符串比较的"兜底"。**兜底本身就是 bug 的温床**：它把
"我不知道"翻译成了一个看起来合法的答案。

**How to apply**：边界处校验并拒绝（400），不要在比较函数里兜底。同类嗅探——
`unwrap_or_default()`、`.ok()` 后继续、解析失败 fallback。

## O-004 CLI 的退出码是契约

**来源**：迭代经验（M01_S01.002）
**上下文**：`cmd_events` 漏了错误检查，把服务端 400 的响应体当事件流打印并 **exit 0**。
脚本化调用完全无法察觉。三个 HTTP 调用点里只有它漏了。

**How to apply**：任何新增的 HTTP 调用点必须走共用的 `get_text()`（它保留服务端
`error` 字段并返回 `Err`）。新增子命令时检查：失败是否 stderr + 非零退出。

## O-005 数据完整性不接受"存在即正确"

**来源**：迭代经验（M01_S01.002）
**上下文**：`ensure_object` 用 `path.exists()` 判断对象已存在就跳过。崩溃写到一半
留下的半个文件会被永久信任，页面永远吐一半内容，**重新发布也不修**。

**修法之所以便宜，是因为 CAS 的性质**：文件名就是内容哈希，所以"长度相符"即可
判定，不需要重算哈希。再配 `write tmp + rename` 保证崩溃不留半个正式名。

**How to apply**：任何"已存在就跳过"的幂等写，都要问：**存在但损坏怎么办？**

## O-006 ponytail：删优于加，但安全与数据完整性不在删的范围

**来源**：用户洞见（`/ponytail` full，用户消息 1 与 5）
**上下文**：用户两次显式加载 ponytail skill，确立 YAGNI 基线。

**边界**（skill 明确豁免、不得简化掉）：信任边界的输入校验、防数据丢失的错误
处理、安全措施、可访问性。

**已按此拒绝的事项**：
- 不为"可测性"把 handler 拆开——那是为测试改架构；HTTP 分支由 12 个黑盒切片覆盖。
- 不为单实现造 trait / 不为固定值造 config。
- 1300 行单文件**不拆**：没有第二个使用方，拆了只是增加跳转成本。

## O-007 发布面的攻击面是"浏览器可达"，不是"网络可达"

**来源**：迭代经验（M01_S01.001）
**上下文**：daemon 只监听回环，容易误判为"没有攻击面"。但**用户浏览器里的任意
网页都能向 127.0.0.1 发请求**，这才是真实攻击面：DNS rebinding（恶意域名解析到
回环）、CORS 简单请求、以及已发布页面之间同源互读。

**已落地的三道线**：Host 固定（只认回环拼写且端口匹配）、写操作 Origin 校验
（CLI 无 Origin 因而不受影响）、响应头加固（nosniff + CSP + 显式 charset）。

**判据**：评估本地服务的安全性时，问的不是"谁能连上端口"，而是"**一个恶意网页
能让浏览器替它做什么**"。

## O-008 注释里的并发模型，要和真实的并发模型核对

**来源**：迭代经验（M01_S01.003，F-3）
**上下文**：修 CAS 时我用 `.{hash}.{pid}.tmp` 做临时文件名，注释写"pid 防止并发
发布互相覆盖"。但真实并发是**同一个 daemon 进程内的多线程** —— pid 全都一样，
临时路径必然冲突，输家 rename 撞 `ENOENT` 返回 500。

**为什么危险**：注释让这段代码"看起来已经处理过并发"，reviewer 和未来的我都会
跳过它。**一条错误的注释比没有注释更糟**。

**How to apply**：写下"这里防了并发"之前，先明确回答——并发单元到底是进程、
线程还是 async task？用什么区分彼此？然后用压测证明，而不是用注释声明。

## O-009 测量工具本身也会骗人

**来源**：迭代经验（M01_S01.003）
**上下文**：`bash suite.sh 2>&1 | tail -16; echo $?` 打印出 `FAIL: ... exited 1`
却显示 `EXIT=0`，我一度以为套件吞掉了失败。实际上 `$?` 拿的是 **`tail` 的**
退出码。不经管道重跑，套件老老实实返回 1。

**How to apply**：验证退出码时不要接管道（或用 `PIPESTATUS[0]` / `set -o pipefail`）。
更一般地——**在断定"被测系统有问题"之前，先排除"测量方式有问题"**。同类陷阱：
读到的是旧的日志快照（本项目也踩过，一份 01:11 的输出被误当成 01:20 的运行结果）。
