# M01_S01.005.FIX — 保留策略实测与"可见性代替删除"

> meta：记录用户提出的"同一地址默认保留 3 个快照"方案的实测评估，以及最终
> 落地的替代方案（把体积做可见，而不是替用户删历史）。
> 触发：用户提出 `设置个默认滚动上限, 同一地址默认 3, 可以通过发布时参数调整,
> 不提供 cli 了, 进修改参数也要推新版本`。
> 状态：**已完成并验收**。

## 用户方案里对的部分

**"不提供 CLI，改参数也要推新版本"这个直觉是对的**，而且比常见做法更好：
保留策略写进发布参数，就和被它管辖的历史存在同一条时间线上，不存在"谁在什么
时候偷偷改了配置导致历史消失"。这是把配置当数据发布，而不是当可变的旁路状态。
它的价值不在省磁盘，在**可追溯**。

## 但 keep=3 的两个前提实测都不成立

### 1. 常见工作负载下回收率 0.2%

30 次发布、170KB bundle 主体不变（前端项目改一个入口文件重发的常态）：

| 项 | 字节 |
| --- | --- |
| keep=3 可释放 | **342**（27 个对象） |
| 必须保留（仍被存活快照引用） | **170,042** |
| **回收率** | **0.2%** |

原因是内容寻址：老快照和新快照**共享绝大多数对象**。删掉 27 个快照行，只有
那 27 个各自独有的小文件失去引用，那个 170KB 的 bundle 一个字节都释放不了 ——
它被最新的 3 个快照引用着。**删掉 90% 的历史，换回 0.2% 的磁盘。**

### 2. pinned URL 会静默漂移（这条是硬伤）

实测：删掉某个 SPA 页面的老快照行后，访问它的 pinned URL：

```
GET /spa/<被驱逐的 snapshot_id>/
HTTP 200
body = NEW-CONTENT                      ← 不是这个版本的内容
x-pageville-version: 7788db11010b       ← 是另一个版本
```

**不是 404，是 200 配错内容。** SPA 回退把任何未命中路径交给 `index.html`，
而 `index.html` 解析到的是当前 latest。HITL 事件信封里记的是 snapshot 版本号，
下游拿着这个 URL 回看"当时用户看到的是什么"，会看到**今天的页面**并以为那就是
当时的现场。这比 404 严重得多 —— 404 是可发现的，200 配错内容不是。

这直接违背产品的核心承诺：`/{page}/{snapshot_id}/` 永不漂移。

## 落地的替代方案：可见性代替删除

既然增长全是**不可回收的历史**（见 [`M01_S01.004`](M01_S01.004.FIX.cas_growth_and_publish_ordering.md)），
诚实的做法是让所有者看见体积并自己决定，而不是替他删。

`daemon status` 现在输出（第一行仍是裸词，保持 shell 判据契约）：

```
running
data_dir=/Users/x/.pageville objects=2 snapshots=1 size=195.3KiB
```

`--json` 增加 `data_dir` / `object_bytes` / `objects` / `snapshots`。

### 过程中发现并修掉的真 bug

第一版把体积算在 **CLI 自己的** `PAGEVILLE_DATA_DIR` 上，而数字其实归**持有端口
的那个 daemon** 所有 —— 用 `--target` 指向另一个 daemon 时，会报一个自信的错误
数字（实测报 0 字节，实际 200KB）。改为由 `/api/v0/health` 从 daemon 侧返回，
daemon 不可达时才回退到本地目录（那也正是两者必然一致的唯一情形）。

**这个 bug 是被新加的验收断言逮住的，不是我复查出来的** —— 断言写对了。

## 量化验收标准

| 指标 | 目标 | 实测 |
| --- | --- | --- |
| `daemon status` 第一行 | 恰好 `running` / `stopped` | 通过（9 处既有断言全绿） |
| 第二行体积明细存在 | 必须 | 通过（grep 断言） |
| 首次发布 200KB 后 `object_bytes` | ≥ 200000 | 通过 |
| 两次不同内容发布后 | 严格增长 | 200002 → 400002 |
| daemon 停止后仍可读 | 必须 | `stopped` + 明细正常 |
| **mutation 验证**：去掉 `.tmp` 跳过 | 单测必须红 | `FAILED` |
| **mutation 验证**：从 CLI 侧读体积 | t007 必须红 | `FAIL: status reported 0 bytes` |
| 验收切片 | 12 全过，退出 0 | 12/12，exit 0 |

## 明确不做的事（及理由）

1. **默认 keep=3** —— 回收 0.2%，代价是 pinned URL 静默漂移。**收益微小、
   代价触及核心承诺**，比例完全不成立。
2. **改成默认关闭的 keep=N** —— 用户不会去开一个省 0.2% 的开关；而真想省空间
   的重度用户，需要的是**按字节**驱逐，不是按个数。按个数在这个 CAS 模型下
   和磁盘占用几乎无关（30 个共享 bundle 的快照 ≈ 1 个的大小）。
3. **发布参数省略时的语义** —— 用户方案没定义"这次发布没带参数"是沿用上次
   还是回到默认。两种都会咬人：沿用则配置变成了不可见的粘滞状态（正好毁掉
   "配置随发布走"的可追溯性初衷）；回默认则某次忘带参数就静默把策略重置了。
   等真要做时必须先定死这条语义。

## 真要做的时候，三个必要条件

1. **按字节预算**，不按个数 —— 个数在共享 CAS 下不反映磁盘。
2. **以事件为根** —— 被 HITL 事件引用过的版本不可驱逐，否则等于毁证据。
3. **留墓碑** —— 驱逐后 pinned URL 必须 410 Gone 并说明被驱逐，绝不能让
   SPA 回退把它变成 200 配错内容。

三条缺一条，就是用"省下 0.2% 磁盘"换"历史链条不可信"。
